# Two verifiers, two demos: keeping Go and Python in step

The verifier exists twice: the Python package in `aqv/` (the reference) and the Go binary
`bin/aqv` (`cmd/aqv`, `internal/aqv`). Both run for now. Each has its own demo pages:

| | Python | Go |
|---|---|---|
| Verifier | `python -m aqv check` | `bin/aqv check` |
| Demo run | `run_demo.py --lang all` → `demo/.work/` | `run_demo.py --lang all --impl go --work demo/.work-go` |
| Pages | [`demo/results/`](../demo/results/index.html) | [`demo/results-go/`](../demo/results-go/index.html) |
| Pages written by | Python (`aqv/html.py`, `demo/run_demo.py`) | Go (`aqv pages`, `internal/aqv/pages.go`) |

The pages are meant to say the same thing. The Go ones carry a "Go verifier" label in their
headings, their footers name the Go command, and the navigation has a "Results (Go)" link.
Everything else should be identical.

## Where parity stands

Parity has five layers. Each has a check, and each check runs on its own.

| Layer | What must match | Check | Result |
|---|---|---|---|
| **1. Helpers** | Mutants, JUnit parsing, test-name matching, word diffs, routes, globs, number and string formatting | `go test ./internal/...` replays answers recorded from Python (`scripts/gen_golden.py`) | Pass: 1,091 code lines (797 mutants), 16 real JUnit reports, and the rest |
| **2. Verifier** | `results.json`, `report.txt`, `report.html` for the same repo | `scripts/parity.py`: Go on the 168 demo repos against Python's results | **168 of 168** |
| **3. Page writers** | Every demo page, from the same data | `scripts/pages_parity.py`: Go and Python render the Go demo run to temporary folders and compare byte for byte | **217 of 217** identical |
| **4. Published pages** | `demo/results` against `demo/results-go`, from two independent demo runs | `scripts/demo_parity.py`: compares them after removing what always differs | **217 of 217**; nothing left unexplained |
| **5. Site pages** | Home page and the two comparison pages | `scripts/site_parity.py`: `aqv site` against the Python writers | **3 of 3** identical |

Layer 4 removes only text that differs between any two runs, whichever verifier made them: object
addresses, random tokens and test-case IDs, ports, durations, timestamps, Rust thread IDs, commit
hashes (each run rebuilds the repo with fresh signed commits), and the Go pages' label, footer and
highlighted nav link. It no longer reorders tests or tolerates any known differences: both verifiers
sort test cases and scrub the checkout path before truncating, so the same commit gives the same
answer wherever it is checked out.

`scripts/parity_all.sh` runs layers 1, 3, 4 and 5 in a minute or two, and layer 2 too with `--engine`
(about an hour). `scripts/check_links.py` checks every link in the published pages.

## What parity doesn't cover

- **The demo harness is Python for both.** `build_baseline.py`, the per-language `stages.py` and
  `edits.sh`, the scenario scripts and `run_demo.py` build the repos and run the scenarios. `--impl go`
  swaps only the verifier. A "Go demo" is Go checking the same repos.
- **The framework page** (`docs/framework.html`) is hand-written HTML, not generated by either side.
- **The Python-only pytest plugin** (`aqv/pytest_capture.py`) stays Python: it runs inside the
  project's own pytest. Go uses the same file.
- **GitHub Actions.** `.github/workflows/parity.yml` is written and validated as YAML, but has not yet
  run on GitHub. Its first run is the real test.

## The plan, and where it ended up

1. **Page writers in Go, with their own page set.** *Done.* `aqv pages` writes `demo/results-go/`.
   Check: `scripts/pages_parity.py`, 217 of 217.

2. **Guards that keep the two in step.** *Done.* `scripts/parity_all.sh`; `scripts/export_langs.py`
   writes `demo/langs.json` so Go reads the language names and stacks from the one place they live.

3. **Fix the truncation difference in both verifiers.** *Done.* A failure message that contains the
   checkout path was cut at a fixed length, so the work folder's name moved the cut. Both verifiers now
   replace the repo path with `<repo>` (and the work folder with `<work>`) before cutting. Checked by
   running the same repo at a short and a very long path: identical reports, Python and Go.

4. **Publish both page sets from the same code.** *Done.* Both demos were rerun from the current code,
   168 of 168 scenarios behaving as expected in each. Layer 4 passes with only run-specific text
   removed. One operational note: the combined run exceeded a two-hour tool limit during the Go demo's
   Rust phase, so Rust and Kotlin were resumed on their own. Nothing was skipped.

5. **Run the gates on every change.** *Done, with one caveat.* Any change to a check, a renderer or a
   runner profile lands in both implementations in the same commit, followed by `scripts/gen_golden.py`
   when a helper changed, then `scripts/parity_all.sh`, and `--engine` before a release or when a
   check's behaviour changed. `.github/workflows/parity.yml` runs this: job `go` (gofmt, vet, test,
   build), job `pages` (published pages and links, from git alone), and job `full` (weekly or on
   demand: both demos, engine parity, page-writer parity). It has not run on GitHub yet.

6. **Decide how far to take Go.**
   - *Site home and comparison pages in Go.* **Done.** `aqv site` writes them; `scripts/site_parity.py`
     shows 3 of 3 byte-identical (a deliberately altered page was detected, so the check can fail).
   - *The harness in Go.* **Not done, on purpose.** The per-language `stages.py` files are data written
     as Python and the scenarios are bash that calls Python helpers. Porting them gives a single
     toolchain and nothing else, and a second harness would be one more thing to keep in step. Revisit
     only if the Python harness becomes a burden.

7. **Retire the Python verifier, if and when.** **Not done: the criteria are not met.**

   | Criterion | Now |
   |---|---|
   | Layers 1 to 5 clean for three releases in a row | 0 of 3: no tags or releases exist yet |
   | Pytest plugin shipped separately from the verifier | Not yet |
   | Golden data regenerated from the last Python release, then frozen | Not yet |
   | Python pages kept published as the reference | Yes (`demo/results/`) |

   Python stays the reference and both verifiers keep running. After retirement the guards would
   compare Go with the frozen reference instead of live Python.

## Differences that are on purpose

| Where | Python | Go |
|---|---|---|
| Page headings | "… · Python (FastAPI …)" | "… · Python (FastAPI …) · Go verifier" |
| Footers and `RESULTS.md` | "Generated by `python demo/run_demo.py`" | "Generated by `python demo/run_demo.py --impl go`" |
| Which nav link is highlighted on the all-languages index | Results | Results (Go) |
| Work folder | `demo/.work` | `demo/.work-go` |

Anything else that differs is a bug in one of them.
